# 승인된 앱·공지 서버 구현

2026-10-08 사용자가 기존 모바일 설계와 서버 구성을 승인했다. Superpowers는 brainstorming만 사용하고 아래 구현은 일반 개발 방식으로 진행한다.

## 구현 순서

1. 별도 ASP.NET 공지 서버와 DB: 초대 가입, 역할, 학급, 교사 담당 범위, 보호자 관계, 공지·첨부·읽음·철회.
2. 교내 서버의 HTTPS 발신 연결: 교직원 계정 상태 검증, 공지 전용 파일, 수신자 확정, 저장된 발송 대기와 재시도·중복 방지, 전송 현황·철회.
3. Windows 공지 작성 화면과 외부 서버 관리자 화면. 실제 학생·보호자 명부 없이 가상 계정으로 검증한다.
4. .NET MAUI Android·iPhone 앱: 분리된 공지/교직원 로그인, 공지·자녀·읽음·첨부, 교사용 작성·현황, 교직원 메시지 조회. 인증 정보는 SecureStorage에 보관한다.
5. Android APK 빌드와 클라이언트·서버 검사. iOS는 Mac·Xcode·서명이 없는 상태에서 검증 완료로 표시하지 않는다.
6. 사용 흐름과 실패 상황을 점검해 개선한다. 우선 후보는 전송 대기·실패 상태, 권한 회수 시 개인정보 제거, 웹 요청 종료의 접근 가능한 확인 화면, 운영·배포 점검 절차다.

## 구체적인 경계

- 공지 서버는 기존 교직원 DB·파일·관리자·원격 지원 경로를 제공하지 않는다. 운영은 독립 호스트·데이터 경로·HTTPS 인증서를 사용한다.
- 외부 명부와 관계는 공지 관리자만 관리하며, 교직원 연결은 학교가 확인한 내부 사용자 ID를 사용한다. 가입 입력으로 역할이나 자녀를 선택할 수 없다.
- 교내 서버가 공지 서비스에 연결해 명부의 공지용 ID·담당 범위를 확인하고 현재 활성 교직원을 검증한다. 비밀번호·해시·개인 쪽지를 전달하지 않는다. 연결 확인이 오래되면 새 공지 발송을 중단한다.
- 학생·보호자 접근은 발송 때 확정한 대상과 현재 학교 확인 관계를 모두 검사한다. 관계·소속 회수 시 기존 대상 접근도 회수하며 새 관계 연결로 과거 비공개 공지를 공개하지 않는다.
- 공지 첨부는 두 서버에서 독립 검사하고 게시 후 30일을 적용한다. 운영 백신이 실패하면 전송을 거부한다. 백업에는 파일 본문을 넣지 않는다.
- 공개 도메인·호스트·서명·스토어 계정은 운영 설정이다. 로컬 검증을 위해 기존 학교 서버의 인터넷 접속이나 방화벽을 변경하지 않는다.
- 백그라운드 푸시는 플랫폼 서비스 자격 증명과 실제 기기 검증이 있어야 운영할 수 있다. 앱 안의 미확인 상태를 먼저 구현하고 실제 푸시를 보낸 것으로 표시하지 않는다.

## 구현·개선 결과

서버 분리, 저장된 발송 대기열, Windows 공지 작성·현황과 외부 관리자 웹, MAUI Android/iPhone 소스를 구현했다. Android Debug·Release 빌드를 확인했고 전용 에뮬레이터에서 실제 앱 흐름 12개를 통과했다. PC·서버 검사와 합쳐 91개를 통과했으며 Windows 실제 키보드 입력 1개는 다른 선택 창이 앞에 있어 보류했다.

사용 흐름을 검토한 뒤 관계 재연결 시 과거 대기 공지 차단, 소속 변경 후 읽음 명단 제한, 대용량 전송과 교사 권한 확인 분리, 학교 Wi-Fi 동시 로그인, 모바일 자동 로그인·화면 가림·파일 선택 중 작성 유지, 누락 입력 수정과 잠긴 패키지 버전의 재현 가능한 빌드를 보완했다. 실제 외부 운영·iOS 검증·푸시·스토어 공개에 필요한 다음 순서는 [운영 안내](mobile-operations.md)에 기록했다.
