# 백엔드 재검토 및 학교 보안 프로그램 호환성

점검일: 2026-10-20. 배포 전 버전 1.0.0을 유지합니다.

## 결론

인증·권한·개인정보 경계·파일 무결성·서버 간 인증·백업·복구·오류 신고를 대상으로 정적 검토와 자동 검사를 수행했습니다. 실제 실행한 14개 검사 묶음의 297개 항목이 통과했습니다. 검사 범위에서 새 인증 우회나 기존 무결성 방어의 회귀는 재현되지 않았습니다. 모든 취약점이 없다는 보증이나 실제 학교 서버의 운영 승인 결과는 아닙니다.

저부하 모드에서 시간표 업로드가 공유 업로드 제한을 적용받지 않는 문제를 수정했습니다. 별도로 현재 PC의 기본 Defender 검사 명령과 운영 모드 업로드가 무해한 파일에서도 실패하는 상태를 재현했습니다. 검사 엔진 연동과 실행 계정은 실제 서버에서 해결해야 하는 배포 전 확인 사항입니다.

이번 PC는 학교 서버로 안내받았던 컴퓨터와 다른 Windows 11 Home·RAM 약 16GB의 사용자 PC입니다. 실제 서버의 백신·방화벽·정책 상태를 이번 결과로 대신할 수 없습니다.

## 확인된 문제와 처리

### P1: 현재 환경에서 운영용 파일 검사가 실패함 — 미해결 운영 조건

현재 PC에서 알약 관련 실시간 서비스는 실행 중이고, Defender의 AMRunningMode는 Not running, WinDefend 서비스는 Stopped로 조회됩니다. 기본 경로의 MpCmdRun으로 무해한 시험 텍스트를 검사했을 때 종료 코드 2와 HRESULT 0x80004005가 반환됐습니다.

이어 별도 가상 DB와 관리자 계정으로 루프백에서만 운영 모드(Production) 서버를 실행했습니다. 같은 종류의 무해한 텍스트를 `/api/attachments`에 올리자 HTTP 422와 “파일 검사 실패 또는 위험 파일입니다.”가 반환됐습니다. 첨부 DB에 등록된 파일은 0개이고 파일 상태는 rejected였으므로 검사에 실패한 파일을 허용하는 우회는 확인되지 않았습니다.

코드 근거:

- `SchoolMessenger.Server/Program.cs`의 일반 첨부 업로드는 MpCmdRun을 직접 실행합니다.
- `SchoolMessenger.Shared/FilePolicy.cs`의 공통 검사는 같은 명령 인자를 사용합니다. 공지 첨부와 시간표 업로드도 이 함수를 호출합니다.
- `School:ScannerPath`·`Portal:ScannerPath`는 실행 경로만 바꿉니다. 알약·V3 실행 파일을 지정한다고 해당 제품의 공식 검사 연동이 되는 구조가 아닙니다.

주의: 이번 검사는 비관리자 계정에서 수행됐습니다. Defender가 중지된 상태와 검사 실패를 확인했지만, HRESULT 하나만으로 알약과의 직접적인 충돌 또는 권한 부족 중 어느 원인이 결정적인지 확정할 수 없습니다. Microsoft도 MpCmdRun의 관리자 권한 실행을 안내합니다. 실제 서버의 운영 계정에서 다시 확인해야 합니다. [Microsoft 검사 명령 설명](https://learn.microsoft.com/en-us/defender-endpoint/command-line-arguments-microsoft-defender-antivirus)

Microsoft 문서상 검사 종료 코드 2는 미치료 탐지뿐 아니라 검사 오류도 포함합니다. 현재의 422 문구만으로 사용자 파일이 악성이라고 판단하면 안 됩니다. 다른 백신 설치 시 Defender가 비활성화되는 것은 Windows 구성에 따라 정상일 수 있으므로, 이를 해결하려고 학교 백신을 중지하거나 Defender를 강제로 활성화하지 않았습니다. [백신 호환성 설명](https://learn.microsoft.com/en-us/defender-endpoint/microsoft-defender-antivirus-compatibility)

보완 방향은 실제 서버에서 학교가 허용한 검사 엔진·공식 호출 방식·반환값·실행 권한을 먼저 확정하고, 검사 불능과 악성 탐지를 구분해 안내·감시하는 것입니다. 검사 성공이 확인되기 전에는 파일을 게시하지 않는 정책을 유지해야 합니다. 실시간 백신이 설치됐다는 사실만으로 업로드 검사 성공을 대신하지 않습니다.

### P2: 시간표 업로드가 저부하 제한에서 빠짐 — 수정 및 검증 완료

기존 `ServerResources.Use`는 첨부 업로드 경로만 공유 업로드 작업으로 분류했습니다. 시간표 가져오기는 별도 동시성 제한 4개를 적용받지만 저부하 모드의 업로드 1개 제한·과부하 확인·진행 중 작업 수에는 포함되지 않았습니다. 따라서 일반 첨부와 시간표 검사가 겹칠 수 있었습니다.

`/api/timetable/import`도 같은 공유 업로드 작업으로 분류하도록 조건 한 곳을 수정했습니다. 기존 권한·CSRF·검사·엑셀 형식 검증은 유지합니다.

회귀 검사는 저부하 모드에서 일반 첨부의 본문 전송을 보류한 뒤 시간표 요청을 헤더만 보냅니다. 수정 전에는 제한을 통과해 업무 경로까지 도달했고, 수정 후에는 본문을 받기 전에 HTTP 429가 반환됩니다. 취소한 업로드의 작업 수가 0으로 돌아오는 것도 검사합니다. 최종 자원 제한 16개와 시간표 통합 21개 검사가 통과했습니다.

### 기존 배포 조건: 전자서명과 포트

- Windows 실행 파일과 설치 파일의 Authenticode 서명이 없는 상태는 그대로입니다. 실행 시험 성공은 모든 단말의 보안 허용을 뜻하지 않습니다.
- 사용자 PC에서 KCaseAgent가 루프백 TCP 8443을 사용 중입니다. 이 PC에 앱 서버까지 설치하면 기본 포트와 충돌합니다. 실제 서버의 점유 상태를 별도로 확인해야 합니다.
- FTP Utility는 TCP 21을 사용 중입니다. 메신저는 FTP를 사용하지 않으며 기본 업무 서버 포트는 7443입니다. 고정 포트 충돌은 확인되지 않았지만 복합기의 실제 스캔 전송은 수행하지 않았습니다.

메일과 운영 검사의 내부 항목은 결과 JSON을 기준으로 계산했습니다. 함수만 내보내는 예약 발송·메시지 회수 모듈을 단독 실행한 결과는 별도 검사로 세지 않았습니다. 해당 검사는 교내 업무 통합 시험에서 실제로 호출됩니다. 수정 후 자원·시간표 검사는 재실행했으며 합계에 중복 가산하지 않았습니다.

두 백엔드는 잠금 파일을 사용한 빌드가 통과했습니다. 서버 2개와 Windows 클라이언트의 NuGet 직접·전이 패키지 취약점 조회도 성공했고 조회 결과에 알려진 취약 패키지는 없었습니다. 이는 운영체제·보안 제품·.NET 런타임 전체의 취약점 판정이 아닙니다.

검사는 순차 실행했고 .NET 프로세서 수를 2로 제한했습니다. 종료 무렵 짧은 3회 관측의 전체 CPU는 8%·14%·3%, 사용 가능 메모리는 약 4.5~4.8GiB였습니다. 전체 시험의 최대 사용량이나 장기·동시 접속 부하를 보장하는 측정은 아닙니다.

## 다음 실환경 검증

1. 실제 학교 서버에서 설치 백신·정책과 서비스 실행 계정을 확인하고, 그 계정으로 무해한 파일의 검사 성공을 재현합니다.
2. 학교가 허용한 제품의 공식 검사 연동이 없으면 임의 CLI 인자를 만들거나 검사를 생략하지 말고 공급업체에 연동 방식을 확인합니다.
3. V3가 실제 설치된 별도 시험 PC와 Defender가 실제 활성화된 별도 시험 PC에서 설치·로그인·업로드·다운로드·원격지원·업데이트를 검증합니다. 현재 학교 PC에 백신을 중복 설치하지 않습니다.
4. GPI와 Zombie ZERO 중앙 관리 화면에서 시험 시간의 탐지·차단·정책 적용 기록을 담당자가 확인합니다. 코드서명·파일 해시·실행 경로를 함께 대조합니다.
5. 복합기에서 실제 스캔 파일을 FTP Utility로 보내는 동안 메신저 첨부 송수신을 시험합니다. 운영 DB와 FTP 수신 폴더는 함께 사용하지 않습니다.
6. 실제 서버 HTTPS·교직원 PC 사이 통신·외부 앱·Cloudflare·백업 장치·UPS·정전 복구는 기존 운영 안내에 따라 별도로 검증합니다.
