# 백업·복구 실행 절차

2026-10-14 추가: [학교 서버·터널 운영 안내](../server-setup-school-tunnel.md)의 새 운영 도구는 선택한 첨부 백업 사본의 원래 만료와 SHA256을 유지하고, 별도 경로의 관리 DB 백업에도 졸업 파기를 적용한다. 해당 백업 경로에 접근하지 못하면 졸업 파기를 완료로 표시하지 않는다. 암호화 장치·키 복구·UPS·망 격리는 실제 학교에서 별도 검증한다.

DB 백업은 온라인 SQLite Backup API, quick_check, foreign_key_check, 임시 파일 생성 뒤 완료 파일 교체를 사용한다. 기본 매일·14일 보관의 기존 정책을 유지한다. 운영자는 School:BackupDirectory / Portal:BackupDirectory를 승인된 별도 저장소로 지정한다. 경로가 다른 물리 디스크인지 코드로 확정하지 않았으며 현재 테스트는 별도 디스크 복구 시험이 아니다.

보관 대상은 DB와 별도로 설정·DataProtection/DPAPI 키·인증서 복구 자료·필요한 유효 첨부다. 승인된 보관 목적/만료를 따르고 백업 접근 권한을 제한한다. 파일 원본이 없는 DB 백업을 완전한 재해 복구 세트라고 부르지 않는다. 학교가 RPO/RTO와 보관·폐기 책임자를 정한다.

1. 두 서비스 중 대상 서비스를 정지하고 관리자 권한·종류·스냅샷 날짜를 확인한다. 운영 중 복원은 `.backend.lock`이 차단한다.
2. 현재 설정과 키를 보호한다. 대상 DB의 현재 상태는 도구가 recovery-backups에 백업한다. 원본 스냅샷은 보존한다.
3. 대상 서버 실행 파일에 `--backend-restore <검증할 백업 절대 경로>`를 주고 School/Portal DataDirectory를 올바르게 지정한다. 명령은 HTTP 서버를 열지 않고 종료한다.
4. 도구는 스냅샷 종류·참조/DB 무결성을 확인하고 준비 DB에서 계정 버전·기기 세션·미사용 초대·교사 연결 증명·미완료 초기 활성화를 폐기한다. 누락 첨부를 삭제 상태로 기록한다.
5. 준비 DB를 SQLite Backup API로 적용하고 재검사한다. 적용 실패 시 복원 전 DB로 되돌린다. 손상 스냅샷 검증 실패 시 운영 DB를 바꾸지 않는다.
6. 서버를 시작해 만료 파일 정리, 교사 연결 재검증, 로그인·권한·공지·시간표·제출 상태를 합성/승인된 사례로 확인한다. 해당 백업 시점 이후 데이터 손실 범위를 기록한다.
7. 백업 시점 이후 탈퇴·관계 해제·권한 축소도 다시 대조한다. 오래된 백업은 그 이후의 조직 변경을 알 수 없다. 연결 키도 필요한 경우 교체하고 운영자 승인을 받아 정상 이용을 연다.

실행 예시는 `13-deployment-runbook.md`에 있다. 실제 학교 DB로 훈련하지 않았다. 키 분실·디스크 전체 손실·정전·별도 디스크 복구는 NOT RUN이다.

복원 시 BackendRecoveryState의 검토 대기를 설정한다. 일반 계정의 업무/학교 소식 이용과 서버 간 전달은 503으로 대기한다. 관리자는 기존 권한 범위에서 명부·관계·권한을 확인할 수 있으며 PC 운영 관리/학교 소식 관리에서 “복원 검토 완료 · 일반 이용 재개”로 명시적으로 확인한다. 교내 확인은 최고관리자만 할 수 있다. 복원된 학생 번호와 미심사 신청도 폐기해 재발급/재신청한다. 이 확인은 학교의 실제 기록 대조를 대신하지 않는다.

복원 대기 동안 교내 일반 관리자의 업무·명부 열람도 막는다. 교내 최고관리자와 별도 학교 소식 관리자만 검토할 수 있다. 백업 이후 바뀐 비밀번호도 현재 기록/담당자와 대조해 필요한 재설정을 수행한다. 세션·초대 폐기가 모든 과거 비밀번호 변경 내역을 자동 복원해주는 것은 아니다.
