# 보안 검사 결과 — 2026-10-08

현재 Windows x64 독립 실행 배포본의 자동·실제 서버·WPF 검사를 55개 통과했고, 보류 항목은 없다. 이는 검사한 조건에서의 결과이며 보안 인증이나 모든 공격에 대한 안전 보장은 아니다. 원본 결과는 `artifacts/test-results.json`에 있다.

## 발견하여 수정한 문제

| 문제 | 수정과 확인 |
| --- | --- |
| 로그아웃 후 복사해 둔 로그인 쿠키를 재사용할 수 있었음 | 로그아웃 때 계정의 세션 버전을 변경한다. 복사한 쿠키와 새 실시간 연결 요청이 거부되는지 검사했다. 같은 계정의 다른 PC·웹 로그인도 만료된다. |
| 계정 변경 뒤 이미 연결한 메시지 알림 연결이 남을 수 있었음 | 메시지·원격 연결의 계정 활성 상태와 세션 버전을 주기적으로 검사하고 연결을 종료한다. 로그아웃과 관리자 계정 비활성화 후 기존 연결 종료를 확인했다. |
| 실시간 연결 경로에 브라우저 출처 검사를 명시할 필요가 있었음 | API와 두 실시간 연결 경로에서 서버 주소와 다른 Origin 및 null Origin을 거부한다. 연결 협상과 WebSocket 경로를 검사했다. |
| 비밀번호 해시 계산 비용이 낮았음 | 표준 ASP.NET Identity의 PBKDF2-HMAC-SHA512를 220,000회로 강화했다. 기존 해시는 정상 로그인 시 교체한다. 저장된 해시 형식과 반복 횟수를 검사했다. |
| 여러 첨부파일 검사가 동시에 서버 자원을 점유할 수 있었음 | 첨부 업로드의 동시 처리 수를 서버 전체 4개로 제한했다. 기존 파일 크기·유형·사용자별 임시 저장량 제한을 유지한다. 이 동시 처리 수에 대한 별도 부하 검사는 아직 하지 않았다. |

브라우저의 쿠키 보호, 스크립트·프레임 제한과 불필요한 카메라·마이크·위치 권한 차단도 적용했다. 운영 HTTPS에서는 로그인 및 CSRF 쿠키의 Secure 속성을 사용한다.

비밀번호 해시 설정은 [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)의 PBKDF2-HMAC-SHA512 기준을 참고했다. 실시간 연결의 브라우저 출처 제한은 [Microsoft SignalR 보안 문서](https://learn.microsoft.com/en-us/aspnet/core/signalr/security?view=aspnetcore-10.0)의 WebSocket 출처 검사 필요성을 참고했다.

## 검사 범위

- 미로그인·승인 대기·비활성 계정 차단, 교직원/관리자 권한, CSRF, 쿠키 재사용 차단과 실시간 연결 회수.
- 개인 메시지와 첨부파일의 수신자 권한, 읽음, 중복 전송, 동시 전송 12건, 오프라인 전달과 서버 재시작.
- 첨부 확장자·파일 시그니처, 30일 만료·물리 삭제. 격리한 운영 모드 테스트에서 백신 경로가 없거나 검사 프로세스가 실패하면 업로드를 거부하고 임시 파일을 지우는지 확인했다.
- 채팅 참여자 권한, 설문 대상자·작성자 권한, 응답·마감·결과, CSV 출력 안전 처리.
- 원격 지원 수락, 직접 TLS 연결, 인증서 지문·패킷 크기·방향 검사, 제어 권한 해제·연결 종료. 서버에 화면·입력 중계 메서드가 없음을 검사했다.
- 실제 WPF 로그인·계정 신청·DPAPI 자동 로그인·자동 실행 설정·쪽지·채팅·설문 화면. 같은 검사 PC에서 직접 연결 두 끝을 실행하여 실제 한글 키보드 입력과 권한 해제 후 입력 차단을 확인했다.

서버·클라이언트의 직접 및 전이 NuGet 패키지를 알려진 취약점 목록으로 조회했으며 해당 시점에 보고된 취약 패키지는 없었다. 이는 이후 공개되는 취약점까지 보장하지 않는다. Windows 방화벽 스크립트는 모의 명령으로 범위·갱신·제거를 검사했으며 이 PC의 실제 방화벽 규칙을 변경하지 않았다.

## 현재 한계와 학교 운영 조건

메시지 본문, 할 일 도입 후 그 내용, SQLite DB·백업과 서버 첨부파일은 애플리케이션 수준에서 암호화하지 않는다. 일반 관리자 화면으로 타인의 개인 메시지를 조회할 수는 없지만 서버 운영체제와 파일에 접근할 수 있는 운영자는 읽을 수 있다. 메시지의 종단 간 암호화는 현재 제공하지 않는다.

Windows 앱의 작성 중 임시 저장도 현재 사용자 데이터 폴더의 JSON이다. 자동 로그인 쿠키에 적용한 DPAPI 보호와는 별개다. 교사용 PC도 개인 Windows 계정, 사용자 폴더 접근 제한과 디스크 암호화가 필요하며 같은 Windows 프로필을 공유하면 작성 중 본문을 사용자 간 격리할 수 없다.

학교에서는 다음 조건을 적용해야 한다.

- 신뢰할 수 있는 HTTPS 인증서, 실제 교직원망 CIDR 제한과 학교 네트워크 정책에 맞는 방화벽 설정.
- 서버 전용 운영 계정, 데이터·백업 폴더의 최소 접근 권한, 공유 폴더 공개 금지, BitLocker 등 서버·백업 저장 장치 암호화.
- 운영 백신의 실제 작동과 검사 권한, Windows 및 포함된 .NET 런타임 업데이트.
- 자동 로그인은 개인 Windows 계정에서 사용. 같은 Windows 계정을 공유하면 DPAPI 보호를 사용자 간 분리로 볼 수 없다.
- 실제 학교 PC 두 대에서 원격 연결·권한 철회, 학교 인증서·VLAN·무선 단말 격리, 교직원 동시 사용 부하를 확인.

이번 검사에서 실제 악성코드 탐지 성능, 학교 PC 두 대 사이의 네트워크, 100명 규모 부하, 서버 디스크 암호화 상태는 검증하지 않았다. 현재 첨부파일 백업은 없으며 DB 백업에는 파일 내용이 들어가지 않는다.

교직원 웹·할 일·파일 제출을 이번 배포본에 구현했다. 추가 검사는 할 일 소유자 권한·변경 충돌·한국 상대 날짜, 제출 파일의 소유권과 일반 첨부 재사용 차단, 최신 제출본만 포함한 ZIP, 파일 만료 후 제출 상태 유지, 일별 알림 중복과 제출·면제·종료 후 중단, 실제 WPF 업무 화면을 포함한다. 제출 현황은 요청자만 전체를 조회하며 수신자는 자기 현황만 본다. 관리자 역할로 타인의 할 일·제출 파일을 조회할 수 없다.

격리한 가상 계정으로 브라우저 로그인, 원문 텍스트 표시, 할 일 후보 확인·수정·등록, 설문 응답 저장, 제출 화면과 로그아웃 후 개인정보 제거를 직접 확인했다. API 파일 전송과 ZIP은 실제 HTTP 검사로 확인했다. 브라우저의 실제 파일 선택 대화상자, 스마트폰 설치, 학교 운영망, 대용량 ZIP 부하와 알림 생성/제출 동시 실행의 부하 검사는 이번 범위에서 확인하지 않았다. 데이터베이스 쓰기 트랜잭션은 제출·종료·면제와 알림 생성의 순서를 보호한다.

학생·학부모의 외부 공지 서비스와 스토어용 모바일 앱은 별도 설계 단계이며 현재 교내 서버의 인터넷 접근을 열지 않았다.
