# 학교 검색과 여러 학교 도입

2026-10-28 · 출시 전 1.0.0

## 사용자 화면

교직원 PC 메신저와 교사용 앱, 학생·학부모용 앱에서 **학교 검색 → 학교명/지역 입력 → 학교 선택 → 로그인** 순서로 사용한다. 같은 이름의 학교는 지역을 함께 표시한다. 선택한 학교는 해당 기기에 기억한다. 학교를 바꾸면 이전 연결의 자동 로그인 정보를 지우고 비밀번호를 비운다. 자동 로그인을 다시 쓰려면 새 학교에서 직접 로그인해야 한다.

교사용은 교내 업무 서버, 학생·학부모용은 학교 소식 서버가 등록된 학교를 보여준다. 교내 업무 서버의 망 제한은 유지한다. 학교를 검색할 수 있어도 교내망/VPN 연결 없이 교직원 업무망에 접속할 수 있게 되는 것은 아니다.

이전 설치의 주소와 자동 로그인은 유지한다. 기존 학교 연결·교내 자동검색·주소 입력은 접힌 **연결 도움 · 관리자 안내를 받은 경우**에 둔다. 학교 등록 후에는 검색에서 선택하면 된다. 원래 있던 계정·메시지·명부를 다른 학교로 옮기거나 통합하지 않는다.

## 구조와 공개 정보

각 학교가 자기 서버와 계정·데이터·약관·책임자·보안 검토 기록을 관리한다. 중앙 검색 목록은 공개 JSON 파일이며 학교명·지역·학교 식별자·역할별 HTTPS 접속 주소만 포함한다. 교직원/학생 명부, 사용자 이름·검색어, 비밀번호·세션·메시지·첨부는 목록 서버에 보내지 않는다. 목록 제공자는 HTTP 접속에 따른 IP·접속 시각 같은 메타데이터를 처리할 수 있으므로 학교 검토자료에 외부 접속 흐름을 포함한다.

목록은 기존 공개 GitHub 저장소의 `codex/school-directory` 브랜치 `schools.json`에서 제공한다. 앱의 신뢰하는 배포 주소는 `config/school-directory.json`을 빌드할 때 포함하며, 내려받은 목록이 배포 주소를 바꿀 수 없다. 이 파일은 학교 서버의 운영 설정이나 개인정보 저장소가 아니다. GitHub의 파일 배포 가용성과 계정 보안에 의존하며 저장소 쓰기 권한을 최소화하고 2단계 인증·변경 검토를 적용한다. 목록 제공에 실패하면 앱에 포함된 목록과 이전 학교 연결을 이용할 수 있다. 포함된 목록이 비어 있으면 새 학교 검색은 온라인 목록이 필요하다.

사용자가 학교를 선택하면 해당 서버의 `/server-info`에서 학교 식별자와 역할을 먼저 대조한다. 일반 TLS 인증서 검증을 유지하고, 주소 이동을 따라가지 않으며, 조회에는 비밀번호·세션 쿠키를 보내지 않는다. 직접 로그인·저장된 로그인 복원·가입 화면 진입 전에 선택한 학교 정보를 확인한다. 목록은 1MB/4,096개, 검색어는 80자, 한 번에 100개 결과, 응답 전체 읽기는 6초로 제한한다. 목록에 등록한 주소의 소유·도입 의사를 확인하는 책임은 등록 담당자에게 있다. 서버가 식별자를 응답한다는 사실만으로 실제 학교의 소유를 입증하지 않는다.

## 학교가 해야 할 일

1. 해당 학교의 서버 두 역할, HTTPS 인증서, 교내망/VPN/학생·학부모 외부 접속 방식과 [학교별 보안 검토](security-regulatory-controls-2026-10-28.md)를 준비한다. 서로 다른 학교의 데이터·키 폴더와 백업은 공유하지 않는다.
2. 운영 설정의 `schoolId`와 보안 검토 JSON의 `schoolId`에 같은 고정 식별자를 넣는다. 영문·숫자·밑줄·하이픈 5~64자다. 학교의 공식 학교 코드를 사용하거나 개발자와 중복 없는 식별자를 정한다. 학생 고유번호나 교직원 이름을 쓰지 않는다. 같은 학교의 두 역할은 같은 식별자를 사용하고, 서로 다른 학교는 다른 식별자를 사용한다.
3. 운영 검토 기록의 `school`에 실제 학교명을 넣고 학교별 약관·문의처도 확정한다. 시험 서버나 임의의 학교를 검색 목록에 등록하지 않는다.
4. 관리자 프로그램에서 해당 운영 서버에 관리자 로그인한다. **운영 현황 → 계정·학교 → 학교 검색 등록자료 저장**을 누른다. 교내 업무 서버와 학교 소식 서버에서 각각 저장하면 `school-registration-office.json`, `school-registration-announcements.json`을 얻는다. 한 역할만 도입하면 해당 파일만 준비한다.
5. 파일에 담긴 주소가 교사 PC 또는 해당 모바일 앱에서 실제로 연결되는지 확인한다. 관리자 PC에서만 통하는 localhost나 임시 주소를 등록하지 않는다. 필요한 경우 관리자가 다른 기기에서 사용할 실제 HTTPS 주소로 접속한 뒤 자료를 다시 저장한다. 공개 목록에 내부 IP를 노출할 필요가 없도록 학교가 검토한 DNS 이름을 사용한다.
6. 개발자에게 등록자료와 지역(예: 전남 여수)을 전달한다. 개발자는 학교의 도입 의사·관리자·주소 소유·학교 식별자를 확인한 뒤 목록에 등록한다. 자동으로 임의 학교가 등록되는 창구는 열지 않는다.
7. 교사와 학생·학부모에게 학교 검색 방법을 안내하고 같은 이름의 다른 학교가 아닌지, 각 앱이 맞는 역할에 연결하는지 시험한다. 기본 비밀번호·최초 활성화·동의·관리자 승인 등 기존 절차를 유지한다.

## 개발자 등록 순서

1. 중앙 브랜치의 최신 `schools.json`을 작업용 폴더에 받는다. 실제 등록자료는 공개 GitHub에 원본 첨부하지 않는다.
2. 프로젝트 루트에서 다음 명령을 실행한다. **실제 파일 경로와 지역으로 바꾼다.** 주소에 접속해 TLS·학교 식별자·이름·역할을 확인하고 로컬 목록만 갱신한다. 접속할 수 없는 교내 서버는 학교의 교내망/VPN에서 수행한다.

```powershell
.\scripts\Update-SchoolDirectory.ps1 `
  -DirectoryPath 'C:\SchoolRegistry\schools.json' `
  -OfficeRegistrationFile 'C:\SchoolRegistry\school-registration-office.json' `
  -AnnouncementsRegistrationFile 'C:\SchoolRegistry\school-registration-announcements.json' `
  -Region '전남 여수'
```

3. 다른 학교의 주소·식별자와 겹치지 않는지 검토한 뒤 `codex/school-directory` 브랜치의 `schools.json`에 게시한다. 도구는 GitHub에 자동 게시하지 않는다. JSON에는 `schema: 1`, `schools` 배열이 있어야 한다. 기존 학교를 한 역할만 갱신하면 반대 역할 주소는 유지한다.
4. 새 설치본을 만들 때 `config/school-directory.json`의 `schools`에 검토한 공개 목록을 반영하면 오프라인 초기 목록도 포함할 수 있다. `sourceUrl`은 앱이 사용하는 신뢰된 목록 배포 주소다. 서버 설치 패키지의 운영 설정과 혼동하지 않는다.
5. 주소·사업자·처리 위치 변경 시 학교 보안 검토와 목록을 함께 갱신한다. 이미 선택한 기기의 주소를 다른 서버로 자동 교체하지 않는다. 변경 후 학교를 다시 검색해 선택하도록 안내한다.

학교 목록에서 삭제해도 학교 서버의 계정·자료를 원격 삭제하거나 서버를 중지하지 않는다. 해당 학교가 계정·운영 종료를 별도로 처리한다. 검색 등록을 보안 인증·교육청 승인으로 표시하지 않는다.

## 출시 상태와 시험

실제 학교 주소를 아직 전달받지 않았으므로 허위 여양고 주소나 시험 학교를 공개 목록에 넣지 않는다. 검색 기능이 있어도 등록 전에는 해당 학교가 결과에 나타나지 않는다. Android·iOS의 소스는 같은 검색 로직을 사용하며 iOS 실제 배포에는 기존 Apple 빌드·서명 절차가 필요하다.

검사는 `tests/SchoolDirectoryChecks`와 기존 메신저 UI/자동 로그인 검사로 실행한다. 서로 같은 이름·다른 지역·다른 식별자의 학교, 서버 역할 불일치, 중복 주소, TLS 오류, 주소 이동, 응답 크기 한도, 비밀번호/쿠키 없는 조회를 확인한다. 실제 운영 전에 학교별 실기기와 망에서 한 번 더 확인한다.
