# GitHub Releases로 배포하기

## 새 버전 생성

1. 소스를 수정하고 `scripts/Build.ps1`과 `node tests/smoke.mjs --ui --package`로 실제 Windows 앱을 확인합니다. 키보드 입력 검증 중에는 테스트 창의 포커스를 유지합니다.
2. 변경 사항을 커밋하고 `main`에 푸시합니다. GitHub Actions의 Verify가 통과하는지 확인합니다.
3. `docs/release-notes.md`에 해당 버전의 변경 사항을 적고 커밋합니다.
4. `git tag v0.1.0-beta.2`와 `git push origin v0.1.0-beta.2`처럼 새 버전 태그를 올립니다. 이미 공개한 태그를 덮어쓰지 않습니다.
5. Release 작업은 잠금 파일 복원, 빌드, 서버 검사, Windows x64 배포본 검사를 실행합니다. 모두 통과하면 ZIP·SHA256SUMS.txt가 포함된 릴리즈 **초안**을 만듭니다. `-beta.1` 같은 버전은 시험판으로 표시합니다.
6. 초안에서 변경 사항과 파일을 확인하고 학교 테스트 PC에서 실행한 뒤 Publish release를 눌러 공개합니다. 초안의 파일은 일반 사용자가 내려받을 수 없습니다.

GitHub에서 별도 비밀번호를 등록할 필요 없이 작업용 GITHUB_TOKEN을 사용합니다. 실제 학교 데이터, 비밀번호, 인증서 개인키는 Git이나 릴리즈에 넣지 않습니다. 소스의 공개와 학교 서버의 외부 공개는 별개이며, 학교 서버를 인터넷에 노출하지 않습니다.

CI는 화면 없는 환경에서 서버 기능을 검사합니다. 실제 WPF UI와 Windows 키보드 입력, 두 PC 간 원격 지원은 현장에서 확인해야 합니다. CI에서 이 항목을 통과했다고 표시하지 않습니다.

## 기존 학교 서버 업데이트

1. 릴리즈 ZIP과 SHA256SUMS.txt를 내려받습니다. PowerShell의 `Get-FileHash .\yymessenger-버전-win-x64.zip -Algorithm SHA256` 결과가 해시 파일과 같은지 확인합니다.
2. 기존 서버와 교사용 앱을 종료합니다. 서버 자동 실행 작업이 있다면 점검 중 재실행되지 않게 합니다.
3. 기존 전체 데이터 폴더(`school.db`, `files`, `keys`, `.initialized` 등)를 별도 위치에 보존하고 데이터 경로·백업 경로·인증서 지문·교직원망 설정을 기록합니다. 현재 자동 DB 백업에는 첨부파일이 없습니다. 점검용 파일 사본에도 기존 30일 만료·삭제 정책과 접근 제한을 적용합니다.
4. 새 ZIP을 별도 폴더에 압축 해제합니다. 실행 파일 교체 시 운영 데이터 폴더를 덮어쓰지 않습니다. 앱과 서버의 버전을 함께 맞춥니다.
5. 기존의 외부 데이터 경로와 인증서·망 설정으로 새 서버를 실행합니다. 데이터 경로가 달라지면 빈 서버로 초기화될 수 있으므로 관리자 비밀번호를 새로 묻는 경우 설정을 먼저 확인합니다.
6. 로그인·받은함·파일 다운로드·제출·웹·원격 지원을 확인한 뒤 교직원에게 새 client 폴더를 배포합니다. 앱 실행 경로가 바뀌면 한 번 실행하여 자동 실행 경로를 갱신하고 원격 지원 방화벽 규칙의 앱 경로도 확인합니다.

오류가 발생하면 서버를 종료하고 점검 전 프로그램·데이터로 복구합니다. 데이터 구조를 변경한 버전은 이전 실행 파일만 교체해서 되돌릴 수 있다고 가정하지 않습니다. 버전별 복구 절차를 릴리즈 노트에 적습니다.

현재 업데이트는 릴리즈 다운로드 후 수동 교체 방식입니다. 앱 내 자동 다운로드·설치는 아직 구현하지 않았습니다. Android·iPhone 앱의 스토어 배포는 별도 단계입니다.
