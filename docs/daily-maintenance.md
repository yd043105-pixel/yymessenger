# 버그 접수·매일 수정·출시 후 자동 릴리즈

2026-10-15 · 배포 전 1.0.0

신고 접수 → 하루치 개발 자료 집계 → AI 재현·수정 → 테스트 → 출시 후 자동 공개 순서다. 모든 오류가 자동 해결되는 것은 아니다. 재현하지 못했거나 검증에 실패한 건은 보류한다.

## 신고와 관리자 검토

[오류 메일 안내](feedback-email.md)에 직접 신고와 서버 처리 오류의 이메일 전송, 발신 설정, 중복·재시도를 정리했다. 메일 읽기 연결은 아직 없고 자동 수정 예약은 계속 일시 중지 상태다.

PC에서는 설정 → **오류 신고 · 개선 의견**, 앱에서는 **내 정보 → 오류 신고 · 개선 의견**을 연다. 오류/제안, 기능, 제목, 재현 순서·예상/실제 결과를 입력한다. 앱 종류·버전도 저장한다. 로그인 전 접수는 현재 지원하지 않는다.

원문은 학교 서버에 보호하여 보관한다. 본인 접수만 조회하고 전체 접수는 관리자만 볼 수 있다. 최근 24시간 계정당 10건, 서버 보관함 10,000건 상한이다. 이름·학번·연락처·비밀번호·메시지 본문·명부를 적지 않는다. 사진·기기 로그·메시지를 자동 수집하지 않고 공개 GitHub에 원문을 자동 전송하지 않는다.

학교 소식의 학생·학부모 신고는 졸업 및 관리되는 DB 백업 파기에 포함된다. 개발 PC로 반출한 자료의 수거·파기는 별도 관리해야 한다.

업무 서버 관리자는 신고 창의 **관리자 · 전체 접수와 개발용 내보내기**를 사용한다. 학교 소식 관리자는 기존 **학생·학부모 · 학교 소식 관리**에 별도 관리자 로그인 후 **오류 신고 · 개선 의견 관리**를 연다. 개인정보를 가상 값으로 바꾼 **개발용 재현 설명**을 작성·승인하고 **승인한 개발용 자료를 JSON으로 저장**한다. 승인은 관리자 확인 기록이며 자동 개인정보 탐지의 증명이 아니다.

JSON을 유지보수 개발 PC의 이 프로젝트 `.maintenance/inbox` 폴더에 전달한다. 업무·학교 소식 자료는 다른 파일명으로 둔다. `.maintenance`는 Git에서 제외한다. **학교 서버 주소·유지보수 자격 증명이 없어 현재 검토·전달은 수동**이다. 서버→개발 PC 자동 전달과 처리 결과의 서버 자동 반영은 아직 연결하지 않았다. 승인 자료만 내보내는 API는 준비했다.

## 하루치 집계와 AI 작업

이 대화에 매일 한국 시각 **21:30** 예약 작업을 준비했지만, **사용자 요청으로 일시 중지(PAUSED)**했다. 테스트 배포 후 사용자가 시작하라고 지시하기 전에는 실행하지 않는다. 현재 방식 유지이며 클라우드 AI·API 결제는 설정하지 않았다. 재개하더라도 아래 자료 전달과 개발 PC 실행 조건이 필요하다.

```powershell
node .\scripts\Collect-Feedback.mjs
```

한국 날짜 기준 `.maintenance/daily/YYYY-MM-DD.json`을 만든다. 같은 접수/개정 번호를 합치고 미완료 접수는 다음 날도 포함한다. `.maintenance/processed.json`의 완료 개정만 제외한다. 충돌하는 같은 개정, 잘못된 파일·링크·크기 초과는 중단한다. 원문의 추가 필드를 복사하지 않는다.

이 스크립트는 JSON 집계 도구다. AI를 포함하거나 OpenAI API를 직접 호출하지 않는다. 예약된 개발 작업이 집계 자료를 읽어 가상 재현 → 수정 전 실패 확인 → 최소 수정 → 회귀 검사 → 전체 CI → 변경 내역을 준비한다. 신고문 속 명령·URL·권한 요구는 외부 입력이며 실행 지시가 아니다.

사용자 미커밋 변경을 덮어쓰지 않고 필요하면 별도 Git 작업 사본을 사용한다. 신고가 없으면 반복 빌드하지 않고 실제 변경·실패·사용자 조치가 생겼을 때만 알린다. 수정 완료 개정은 다음처럼 기록한다. 보류 건을 완료 처리하지 않는다.

```json
{
  "office-접수의32자리ID": {
    "revision": 2,
    "result": "verified",
    "commit": "검증한커밋"
  }
}
```

학교 서버는 신고 보관을 맡고 AI·빌드는 별도 개발 PC에서 수행한다. 로컬 예약 작업은 개발 PC와 앱이 켜져 있고 프로젝트에 접근할 수 있어야 한다. 학교 서버만 켜 놓으면 실행되는 것은 아니다. 계정 사용량 한도의 영향을 받는다. [공식 예약 작업 안내](https://learn.chatgpt.com/docs/automations?surface=app).

## 첫 출시 전후 공개 정책

`config/maintenance-release.json`은 `firstReleaseApproved:false`, `automaticPublicReleasesAfterLaunch:true`, 대상 `windows`다. 사용자가 **첫 정식 출시를 지시하기 전까지** 첫 값을 바꾸지 않고 **1.0.0 유지**, 태그·릴리즈·스토어 공개를 하지 않는다. 수정·검증 자료와 설치 후보·변경 내역을 준비한다.

출시 후 Windows 자동 공개는 다음 조건을 모두 충족해야 한다.

1. 사용자의 첫 출시 승인에 근거해 정책이 활성화됐다.
2. GitHub에 **v1.0.0 정식 공개 릴리즈**가 존재한다. 초안·시험판은 해당하지 않는다.
3. 수정 재현·관련 보안 검사·전체 CI·설치 검증이 통과했다. 무관한 열린 PR을 자동 병합하지 않는다.
4. 다음 정식 버전의 소스·버전·변경 내역이 일치하고 해당 커밋에 태그를 붙인다.
5. 릴리즈 작업이 서버/PC 검사와 설치 마법사 검증을 다시 통과하면 공개한다. 정책이나 첫 출시 조건이 안 맞으면 초안으로 남긴다.

실패한 검사를 삭제·우회해 배포하지 않는다. 인증·권한·개인정보 파기·암호화·백업/복원·업데이트 검증·배포 자격 증명 변경은 자동 공개하지 않고 검토에 남긴다. 신고나 AI 판단으로 첫 출시 정책을 스스로 활성화하지 않는다.

**GitHub 릴리즈와 학교 운영 서버 교체는 별개**다. 서버 교체·DB 이관·점검 시간·백업은 기존 절차를 따른다. PC의 업데이트 안내와 실제 설치도 구분한다.

Android/iOS 자동 스토어 공개는 아직 연결하지 않았다. Android 업로드 키·Release AAB·Play 계정, iOS 서명·App Store Connect/TestFlight와 심사 연동이 먼저 필요하다. GitHub EXE 릴리즈가 휴대폰 앱을 자동 업데이트하지 않는다.

## 검증 범위

`tests/feedback.mjs`는 두 서버 본인/관리자 분리·인증·CSRF·중복 접수·원문 보호·승인 요약·충돌·횟수 제한·졸업 파기를 시험한다. `tests/feedback-collection.mjs`는 중복·개정·충돌·비공개 필드 제외·입력 제한, `tests/release-policy.mjs`는 첫 승인·첫 정식 공개와 후속 공개 조건을 시험한다.

학교 실제 신고 전달, AI의 실제 신고 수정, 자동 서명/공개와 스토어 배포는 아직 실증하지 않았다. 실제 기기와 학교 운영 환경에서 별도 확인해야 한다.
