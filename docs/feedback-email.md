# 오류 신고를 이메일로 받기

2026-10-15 · 배포 전 1.0.0. 실제 학교 SMTP 인증과 메일 도착은 아직 확인하지 않았다. 하루 한 번 메일을 확인하고 수정하는 예약 작업은 **일시 중지(PAUSED)** 상태를 유지한다.

## 메일 형식과 전송 범위

제목 예시: **`[여양메신저 오류로그]10월15일14시05분 김동욱 오류`**.

시각은 접수 시각을 한국 시간으로 바꾸고 이름은 해당 서버에 로그인한 계정의 학교 등록 이름을 사용한다. 클라이언트가 보낸 이름이나 메일 주소를 그대로 사용하지 않는다. 수신 주소는 두 서버의 로컬 운영 설정에만 기록하며 공개 소스·기본 설정·설치 파일에 넣지 않는다.

다음 경우에 메일 발송 대기열에 들어간다.

- 사용자가 PC 설정 또는 앱 내 정보에서 **오류 신고**를 접수한 경우. 개선 의견은 메일을 만들지 않는다.
- `automaticBugReportsEnabled`를 켰을 때 로그인한 사용자의 API 처리에서 서버 오류(5xx)가 발생한 경우. 같은 사용자·앱·버전·경로 양식·오류 유형은 최근 30분 동안 중복 접수를 줄인다.

권한 없음·로그인 만료·유효성 검사 실패 같은 정상적인 4xx 응답은 자동 신고하지 않는다. 오류 신고 API 자체의 실패는 재귀 신고하지 않는다. 계정당 최근 24시간 10건과 서버 보관함 10,000건 제한을 함께 적용한다. 로그인 전 실패·서버가 꺼진 상태·인터넷 단절·앱 화면의 논리 오류·OS 강제 종료를 모두 자동 감지하는 기능은 아니다. 감지되지 않는 문제는 직접 신고한다.

메일에는 앱 종류·버전·기능·접수 번호를 넣는다. 서버가 자동 생성한 기술 진단이 있으면 오류 유형, **실제 URL 대신 경로 양식**, 추적 번호, 앱 코드의 클래스/메서드와 줄 번호를 넣는다. 예외 메시지·요청 본문·쪽지 내용·첨부·비밀번호·파일의 전체 경로는 포함하지 않는다. 소스 위치가 없으면 줄 번호는 0일 수 있다. 직접 쓴 신고 제목·설명은 관리자 프로그램에서 확인한다.

등록된 이름은 메일에 포함된다. 수신함 사본은 앱의 졸업 파기 작업으로 지워지지 않으므로 학교가 정한 메일 보관·삭제 기준에 따라 별도 관리한다.

## 실제 학교 서버에서 설정할 순서

1. 각 VM에서 기존 `server-operations.local.json`을 연다. 프로젝트의 로컬 준비본은 `artifacts/server-operations-personal-settings/office`와 `announcements`에 있다. 현재 지정한 수신 주소와 두 활성화 값을 넣어 뒀지만 발신 인증은 아직 없다. 개인 설정 폴더 전체를 GitHub·배포 ZIP에 넣지 않는다.
2. 실제 학교가 허용한 발신 계정과 SMTP를 정한다. 현재 구현은 기존 장애 알림과 같은 SMTP 인증을 재사용하며 **587/STARTTLS**를 사용한다. 학교가 허용한 발신 계정과 수신 계정은 달라도 된다.
3. 로컬 설정의 `alerts.sender`, `alerts.smtpHost`, `alerts.smtpPort`, `alerts.recipient`를 실제 값으로 채운다. `feedbackEmailEnabled:true`, `automaticBugReportsEnabled:true`를 확인한다. 공개 예시는 두 기능 모두 `false`다.
4. 처음 설치할 때 기존 `Configure-ServerOperations.ps1 -InitializeSecrets -Apply` 절차에서 발신 인증 정보를 숨김 입력한다. 비밀 파일이 이미 있으면 초기화로 덮어쓰지 않고 기존 장애 알림의 SMTP 인증을 재사용한다. 일반 계정 비밀번호나 앱 비밀번호를 채팅·명령 인수·소스에 적지 않는다.
5. Gmail을 발신 계정으로 쓰고 이 방식을 지원하는 계정이면 2단계 인증과 앱 비밀번호를 준비한다. 계정 유형·보호 설정에 따라 앱 비밀번호가 제공되지 않을 수 있다. [Google 공식 안내](https://support.google.com/accounts/answer/185833?hl=ko)를 확인한다.
6. 학교 서버에서 `Server-Operations.ps1 -Mode TestEmail`로 기존 알림 메일 도착을 시험하고, 점검 시간에 같은 전용 운영 계정으로 서버를 재시작한다. `Start`가 보호된 SMTP 인증을 서버 프로세스에 전달한다. EXE만 따로 실행하면 이 운영 설정이 전달되지 않을 수 있다.
7. 가상 시험 계정으로 직접 오류 신고를 한 번 제출한다. **관리자 → 오류 신고 관리**의 메일 활성·발신 설정·대기/발송/실패 수를 확인하고 실제 수신함·스팸함에서 도착을 확인한다. SMTP 서버 수락 기록이 최종 수신함 도착의 증명은 아니다.

SMTP 인증이 없거나 기능이 꺼져 있어도 신고 접수는 보관한다. 메일이 준비되지 않았다는 이유로 정상 메신저 기능을 중단하지 않는다. 준비 후에는 남은 대기 건도 처리된다.

## 부하·재시도·중복

서버마다 1분 간격으로 한 건씩 처리하며 SMTP 요청은 10초 뒤 취소한다. 큰 로그 압축·이미지·첨부를 만들지 않는다. 접수와 발송 대기열은 같은 DB 트랜잭션으로 저장하고, 같은 신고 재전송이 새 메일을 만들지 않게 한다.

발송 실패는 DB에 남겨 1·2·4분 등으로 간격을 늘려 최대 8회 시도한다. 실패한 SMTP 오류의 원문은 저장하지 않는다. 8회 실패 후 관리자가 발신 설정을 확인하고 **실패한 메일 다시 보내기**로 재시도한다. 재시작해도 대기열과 시도 횟수는 유지된다. 학생·학부모의 졸업 파기 때 해당 원문과 미발송 대기열도 제거한다.

SMTP의 수락과 DB의 완료 기록은 하나의 트랜잭션이 될 수 없다. 수락 직후 정전·연결 중단 또는 과거 DB 복원 시 드물게 같은 메일을 다시 받을 수 있다. 같은 접수 번호와 일정한 Message-ID로 구분하도록 했으며, 완전한 ‘정확히 한 번’ 배달을 보장하지 않는다.

## 하루 한 번 확인하고 수정하기

메일 수신과 AI의 메일 열람은 별개다. 현재 Gmail 수신함을 읽는 연결은 없으며 메일 읽기·자동 수정 예약도 중지돼 있다. 테스트 배포 후 사용자가 시작하라고 할 때, Gmail 읽기 연결과 접근 범위를 확인해 지정 제목의 오류 메일만 하루 한 번 확인하도록 연결한다. 그때까지 실제 Gmail 열람·자동 수정·릴리즈는 실행하지 않는다.

현재 메일 대기열과 제목·재시도는 가상 발송으로 검사한다. 실제 발신 계정 인증, 학교 회선 SMTP 허용 여부, 수신함 도착, 모바일 실기기의 오류 자동 접수는 학교 시운행에서 따로 확인해야 한다.
